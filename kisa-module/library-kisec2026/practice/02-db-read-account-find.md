# 실습 02 — DB에서 데이터를 조회하는 기능에 대한 설계단계 보안약점 진단

| 입력데이터 검증 및 표현 | **웹 기반 중요기능 수행 요청 유효성 검증** (DSG-IV-06) | 아이디·비밀번호 찾기(인증정보 조회·임시비밀번호 발송)는 중요기능이므로, 자동화 공격으로 계정정보를 대량 수집·열거하지 못하도록 정상 요청 여부 검증(CSRF 토큰·CAPTCHA) 설계 | 계정 열거·자동화 공격 방지 |

| 보안기능 | **중요정보 전송** (DSG-SF-08) | 임시 비밀번호를 이메일로 발송 시 안전한 전송, 입력 개인정보(이름·이메일·아이디) 전송 구간 TLS 암호화 설계 | 인증정보 전송 암호화 |
| 보안기능 | **인증수행 제한** (DSG-SF-02) | 아이디/비밀번호 찾기 시도 횟수 제한 및 초과 시 제한 정책, 실패 시도 로깅 설계로 무차별 계정 탐색 차단 | 반복 조회 시도 제한 |
| 에러처리 | **예외처리** (DSG-EH-01) | 계정 존재여부·조회 실패에 대해 상세 에러나 차등 응답으로 계정 존재를 유추할 수 없도록 일관된 메시지·지정 에러페이지 처리 설계 | 계정 존재여부 노출 방지 |

## 💡 진단 해설

아이디/비밀번호 찾기는 **개인정보를 입력받아 DB를 조회(SELECT)하고 그 결과(아이디·계정 존재여부)를 사용자에게 반환**하는 기능이다. 입력값이 그대로 쿼리에 들어가고 조회결과가 화면·이메일로 나가므로 입력검증·결과노출·계정열거가 핵심 위험이다.

### DSG-IV-01 — DBMS 조회 및 결과 검증
- **적용 이유**: 이름·이메일·아이디로 매칭 계정을 SELECT 조회한다. 이 입력값이 쿼리 구조를 바꿀 수 있으면 SQL 삽입으로 타인 인증정보를 무단 조회할 수 있다.
- **설계단계 진단방법**: **요구사항정의서**에 정적쿼리 사용 대책이 있고, **아키텍처설계서**에 PreparedStatement/ORM 적용계획이 있으며 **요구사항추적표**로 추적되는지 확인한다. **개발가이드**에 동적쿼리 불가피 시 입력값 필터링 규칙이 있는지, **단위테스트케이스**에 입력값이 쿼리 구조를 변경하는지 점검 계획이 있는지 본다.
- **결함 포인트**: 이름·이메일을 문자열 결합으로 조회 쿼리에 넣는 동적 SQL 설계.

### DSG-IV-06 — 웹 기반 중요기능 수행 요청 유효성 검증
- **적용 이유**: 찾기 기능은 인증정보 조회·임시비밀번호 발송이라는 중요기능이다. 검증이 없으면 자동화 스크립트로 이름·이메일 조합을 대입해 가입 회원을 열거하거나 임시 비밀번호 메일을 폭주시킬 수 있다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 CSRF 토큰·CAPTCHA 등 정상요청 판별 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 위조·반복요청 차단 점검 계획이 있는지 확인한다.
- **결함 포인트**: 찾기 요청에 자동화·위조요청 방지 설계가 없는 경우.

### DSG-IV-05 — 웹 서비스 요청 및 결과 검증
- **적용 이유**: 조회된 아이디·이름 등 DB조회결과를 응답페이지에 출력한다. 저장된 값에 스크립트가 포함되어 있으면 출력 시 XSS가 실행된다.
- **설계단계 진단방법**: **아키텍처설계서·개발가이드**에 DB조회결과 출력 시 HTML인코딩/XSS 필터링 규칙이 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 출력값 XSS 필터링 점검 계획이 있는지 확인한다.
- **결함 포인트**: 조회결과를 인코딩 없이 화면에 그대로 출력하도록 설계한 경우.

### DSG-SF-03 — 비밀번호 관리
- **적용 이유**: 비밀번호 "찾기"는 평문 복원이 아니라 재설정이어야 한다. 임시 비밀번호 생성·발송 방식이 부실하면 계정이 탈취된다.
- **설계단계 진단방법**: **요구사항정의서**에 비밀번호는 솔트 적용 일방향 해시로 저장되어 복호화 불가하므로 임시 비밀번호 발급(재설정) 방식으로 설계되었는지, 임시 비밀번호가 안전한 난수로 생성·1회용·로그인 후 즉시 변경 유도되는지 확인하고, **요구사항추적표**로 추적되는지 본다.
- **결함 포인트**: 저장된 비밀번호를 복호화해 그대로 안내하거나, 추측 가능한 임시 비밀번호(예: 생년월일)를 발급하도록 설계한 경우.

### DSG-SF-08 — 중요정보 전송
- **적용 이유**: 임시 비밀번호를 이메일로 발송하고, 이름·이메일·아이디 같은 개인정보를 클라이언트→서버로 전송한다. 평문 전송 시 가로채기 위험이 있다.
- **설계단계 진단방법**: **아키텍처설계서**에 입력 개인정보 전송 구간 TLS 암호화와 임시 비밀번호 발송 채널 보호 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 전송구간 암호화 점검 계획이 있는지 확인한다.
- **결함 포인트**: 찾기 폼을 HTTP 평문으로 전송하거나 임시 비밀번호를 안전하지 않게 노출하는 설계.

### DSG-SF-02 — 인증수행 제한
- **적용 이유**: 찾기 화면은 이름·이메일·아이디 조합을 반복 대입해 유효 계정을 탐색하는 무차별 공격 표적이 된다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 찾기 시도 횟수 제한·초과 시 제한(잠금·추가입력 요구) 정책과 실패 시도 로깅 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 시도횟수 제한 점검 계획이 있는지 확인한다.
- **결함 포인트**: 조회 시도 횟수에 제한이 없어 자동화 대입이 무제한 가능한 설계.

### DSG-EH-01 — 예외처리
- **적용 이유**: "계정이 존재할 경우 임시 비밀번호를 발송"하는 흐름은 응답이 달라지면 계정 존재여부(개인정보)가 유추된다. 또한 조회 실패 시 상세 에러가 노출되면 DB 구조가 드러난다.
- **설계단계 진단방법**: **요구사항정의서·개발가이드**에 계정 존재여부와 무관하게 일관된 안내 메시지를 반환하고, 상세 에러정보 대신 지정 에러페이지로 처리하도록 설계되어 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 에러를 통한 정보노출 점검 계획이 있는지 확인한다.
- **결함 포인트**: "존재하지 않는 계정입니다"처럼 계정 존재여부를 구분 노출하거나, 예외 발생 시 스택트레이스·SQL 오류를 그대로 노출하는 설계.

> 공통: 각 보안설계기준은 **요구사항정의서 → 아키텍처설계서 → 개발가이드 → 요구사항추적표 → 단위테스트케이스** 의 연결고리가 끊기지 않는지를 보는 것이 설계단계 진단의 핵심이다.
