# 실습 01 — DB에 데이터를 입력하는 기능에 대한 설계단계 보안약점 진단

> 출처: KISEC 2026 기본과정 교재 p302–304 (Ⅳ-02 보안설계 기준 및 설계 기준 실습)
> 형식: 참고자료(p302 화면정의 · p303 입출력/업무흐름)를 보고 **p304 「보안 설계 기준」 양식**을 채우는 실습

**업무흐름**: ① 회원정보 입력 → ② 중복아이디 검색(DB 조회) → ③ 우편번호 외부링크 검색 → ④ 첨부파일(인증서) 업로드 → ⑤ 가입신청 시 DB에 회원정보 추가

| 입력데이터 검증 및 표현 | **업로드·다운로드 파일 검증** (DSG-IV-10) | 인증서 첨부파일의 확장자·크기·콘텐츠 검증 및 실행권한 제거, 저장경로 분리 설계 | 위험 형식 파일 업로드 방지 |
| 보안기능 | **인증 대상 및 방식** (DSG-SF-01) | 회원가입 본인확인 인증 방식(이메일·휴대폰 등) 정의 | |

| 보안기능 | **중요정보 저장** (DSG-SF-07) | 개인정보(법령상 암호화 대상)의 암호화 저장 설계, 저장 후 메모리 0 초기화 | |
| 보안기능 | **중요정보 전송** (DSG-SF-08) | 비밀번호·개인정보 전송 구간 TLS 1.2 이상 암호화 설계 | |

## 💡 진단 해설

회원가입 화면은 **DB 입력(INSERT) + 개인정보 처리 + 인증 + 파일 업로드 + 외부링크 연동**이 한 화면에 결합된 기능이라, 입력데이터 검증·보안기능 영역의 설계항목이 모두 관련된다. 각 보안설계기준에 대해 ① 왜 이 화면에 적용되는지, ② 설계단계에서 어떤 산출물을 어떻게 검토하는지를 정리한다.

### DSG-IV-01 — DBMS 조회 및 결과 검증
- **적용 이유**: 가입신청 시 회원정보를 DB에 추가(INSERT)하고, 중복아이디 검색을 위해 입력한 아이디로 DB를 조회(SELECT)한다. 이때 외부입력값(아이디·이름 등)이 SQL 질의문 구조에 영향을 주면 SQL 삽입이 가능하다.
- **설계단계 진단방법**: **요구사항정의서**에 "외부입력값이 삽입되는 SQL을 동적 생성하지 않는다(정적쿼리 사용)"는 대책이 정의되어 있고, **아키텍처설계서**에 PreparedStatement·MyBatis `#{}`·ORM 적용계획이 있으며, **요구사항추적표**로 추적되는지 확인한다. **개발가이드**에 정적쿼리 시큐어코딩 규칙과 동적쿼리 불가피 시 입력값 필터링 방법이 기술되어 있는지, **단위테스트케이스**에 "입력값이 쿼리 구조를 변경시키는지" 점검 계획이 있는지 본다.
- **결함 포인트**: 아이디·이름을 문자열 결합으로 쿼리에 넣는 동적 SQL 설계, DB연결 계정에 과도한 권한 부여.

### DSG-IV-06 — 웹 기반 중요기능 수행 요청 유효성 검증
- **적용 이유**: 가입신청 버튼 클릭은 회원정보를 DB에 추가하는 **중요기능 수행 요청**이다. 위조된 요청·자동가입 봇이 정상 사용자의 요청인지 검증해야 한다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 세션별 CSRF 토큰 발급/검증, CAPTCHA 같은 상호처리 기법 적용계획이 있는지, **요구사항추적표**로 추적되는지 확인하고, **단위테스트케이스**에 위조요청 차단 점검 계획이 있는지 본다.
- **결함 포인트**: 중요기능 요청에 유효성 판별(토큰·재인증) 설계가 누락된 경우.

### DSG-IV-07 — HTTP 프로토콜 유효성 검증
- **적용 이유**: 우편번호는 외부링크(자동연결 URL)로 연결되어 값을 검색한다. 신뢰되지 않은 URL로 자동 접속하면 피싱·SSRF·오픈리다이렉트 위험이 있다.
- **설계단계 진단방법**: **개발가이드**에 자동연결 URL의 신뢰 도메인 화이트리스트 검증 규칙이 정의되어 있는지, **요구사항정의서·요구사항추적표**로 외부링크 검증 대책이 추적되는지 확인한다.
- **결함 포인트**: 외부 우편번호 서비스 URL을 검증 없이 그대로 연결하도록 설계한 경우.

### DSG-IV-10 — 업로드·다운로드 파일 검증
- **적용 이유**: 사용자가 인증서를 첨부파일로 업로드한다. 위험 확장자(.jsp/.php 등) 웹셸이 업로드·실행되면 서버가 장악될 수 있다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 업로드 파일의 타입·크기·개수·실행권한 제한 정책과 외부에서 식별 불가능한 저장경로·랜덤 파일명 설계가 있는지, **개발가이드**에 확장자 화이트리스트·실행권한 제거 규칙이 있는지, **단위테스트케이스**에 위험형식 업로드 차단 점검 계획이 있는지 확인한다.
- **결함 포인트**: 확장자/콘텐츠 검증 없이 업로드 허용, 웹 루트 하위에 원본 파일명 그대로 저장.

### DSG-SF-01 — 인증 대상 및 방식
- **적용 이유**: 회원가입은 본인확인(이메일·휴대폰 등) 인증이 동반되는 기능이다. 인증방식 정의가 없으면 명의도용 가입이 가능하다.
- **설계단계 진단방법**: **요구사항정의서**에 가입 시 본인확인 인증 대상·방식이 정의되어 있고 우회 불가하도록 설계되었는지, **요구사항추적표**로 추적되는지 확인한다.

### DSG-SF-03 — 비밀번호 관리
- **적용 이유**: 화면에서 비밀번호·비밀번호 확인·비밀번호 힌트·비밀번호 정답을 입력받아 DB에 저장한다. 생성규칙·저장방식이 부실하면 계정 탈취로 이어진다.
- **설계단계 진단방법**: **요구사항정의서**에 KISA 『패스워드 선택 및 이용 안내서』 생성규칙(2종 이상·8자리 또는 10자리 이상), **솔트가 적용된 일방향 해시 + 서버 측 해시 실행** 저장 정책, 재설정/변경 규칙이 정의되어 있는지, **개발가이드**에 해시함수·솔트 적용 시큐어코딩 규칙이 있는지, **요구사항추적표**로 추적되는지 확인한다.
- **결함 포인트**: 비밀번호를 평문/단순 해시(솔트 없음)로 저장, **특히 비밀번호 힌트·정답을 평문 저장**하면 비밀번호 추정 단서가 노출되는 결함.

### DSG-SF-07 — 중요정보 저장
- **적용 이유**: 입력받는 회원정보는 아이디·패스워드를 포함한 개인정보다. 법령상 암호화 대상 개인정보를 DB에 평문 저장하면 유출 시 피해가 크다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 암호화 대상 정보 식별과 안전한 암호알고리즘·키 적용 저장 정책이 명시되어 있는지, 사용 후 메모리 0 초기화·캐싱 제한 설계가 있는지, **요구사항추적표**로 추적되는지 확인한다.
- **결함 포인트**: 주민등록번호·비밀번호 등 암호화 대상 개인정보를 평문으로 DB에 INSERT하도록 설계한 경우.

### DSG-SF-08 — 중요정보 전송
- **적용 이유**: 비밀번호·개인정보가 클라이언트→서버로 전송된다. 평문 전송 시 네트워크 구간에서 가로채기가 가능하다.
- **설계단계 진단방법**: **아키텍처설계서**에 인증정보·개인정보 전송 구간 TLS 등 통신 암호화 적용계획이 있는지, **요구사항추적표**로 추적되는지 확인하고, **단위테스트케이스**에 전송구간 암호화 점검 계획이 있는지 본다.
- **결함 포인트**: 회원가입 폼을 HTTP(평문)로 전송하도록 설계한 경우.

> 공통: 각 보안설계기준은 **요구사항정의서(대책 정의) → 아키텍처설계서(적용계획) → 개발가이드(구현규칙) → 요구사항추적표(추적) → 단위테스트케이스(점검계획)** 의 연결고리가 끊기지 않는지를 보는 것이 설계단계 진단의 핵심이다.
