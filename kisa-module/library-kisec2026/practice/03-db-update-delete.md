| 보안기능 | **중요자원 접근통제** (DSG-SF-04) | 게시글 수정/삭제 요청 시 요청자가 해당 게시글의 작성자(또는 권한 보유자)인지 서버에서 검증, 게시글 식별자 변조로 타인 글을 수정/삭제하지 못하도록 객체 단위 접근통제(권한 검증) 설계 | 권한 없는 수정/삭제 방지 |

| 입력데이터 검증 및 표현 | **웹 서비스 요청 및 결과 검증** (DSG-IV-05) | 수정된 게시글 내용·목록을 응답페이지에 출력할 때 HTML인코딩/XSS 필터링 설계 (저장형 XSS 방지) | XSS 방지 |
| 세션통제 | **세션통제** (DSG-SC-01) | 수정/삭제 요청 처리 시 로그인 세션 검증, 세션 간 데이터 비공유, 세션ID 안전 관리(재로그인 시 변경·만료) 설계 | 세션 위·변조 방지 |

## 💡 진단 해설

게시물 수정/삭제는 **DB의 기존 데이터를 변경(UPDATE)·제거(DELETE)하는 상태변경 기능**이다. 핵심 위험은 "내가 권한 없는 글을 수정/삭제할 수 있는가"(접근통제)와 "위조된 요청으로 내가 모르게 수정/삭제가 일어나는가"(CSRF)이다.

### DSG-SF-04 — 중요자원 접근통제
- **적용 이유**: 게시글은 작성자만 수정/삭제할 수 있어야 하는 중요자원이다. 화면은 클릭으로 글 ID를 넘기는 구조라, 요청 파라미터의 글 ID를 변조하면 타인 게시글을 수정/삭제할 수 있는 권한 없는 접근(직접객체참조)이 발생한다.
- **설계단계 진단방법**: **요구사항정의서**에 게시글 수정/삭제 시 요청자=작성자(또는 권한자) 여부를 서버에서 검증한다는 접근통제 정책이 정의되어 있는지, **아키텍처설계서**에 객체 단위 권한 검증(소유자 확인, RBAC/비즈니스 로직 접근통제) 적용계획이 있는지, **요구사항추적표**로 추적되는지 확인한다. **단위테스트케이스**에 타인 글 ID로 수정/삭제 시도 차단 점검 계획이 있는지 본다.
- **결함 포인트**: 화면에 수정/삭제 버튼이 보이는지로만 통제하고 서버에서 소유자 검증을 하지 않아, 글 ID만 바꾸면 타인 글이 변경/삭제되는 설계.

### DSG-IV-06 — 웹 기반 중요기능 수행 요청 유효성 검증
- **적용 이유**: 수정/삭제는 DB 상태를 변경하는 중요기능이다. 검증이 없으면 공격자가 위조한 링크/폼으로 로그인한 사용자가 의도치 않게 자신의 글을 수정/삭제하도록 유도(CSRF)할 수 있다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 세션별 CSRF 토큰을 생성·세션에 저장하고 요청 시 일치 검증하는 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 토큰 없는/위조 요청 차단 점검 계획이 있는지 확인한다.
- **결함 포인트**: 수정/삭제 요청에 CSRF 토큰 등 정상요청 판별 설계가 누락된 경우.

### DSG-IV-01 — DBMS 조회 및 결과 검증
- **적용 이유**: 게시글 ID 등 외부입력값으로 UPDATE/DELETE/SELECT를 수행한다. 입력값이 쿼리 구조를 바꾸면 SQL 삽입으로 다량의 데이터가 변조·삭제될 수 있다.
- **설계단계 진단방법**: **요구사항정의서**에 정적쿼리 사용 대책, **아키텍처설계서**에 PreparedStatement/ORM 적용계획이 있고 **요구사항추적표**로 추적되는지, **개발가이드**에 동적쿼리 시 입력값 필터링 규칙이 있는지, **단위테스트케이스**에 입력값의 쿼리 구조 변경 여부 점검 계획이 있는지 확인한다.
- **결함 포인트**: 글 ID를 문자열 결합으로 DELETE/UPDATE 쿼리에 넣는 동적 SQL 설계.

### DSG-IV-05 — 웹 서비스 요청 및 결과 검증
- **적용 이유**: 수정된 게시글 내용과 목록이 응답페이지에 출력된다. 게시글 본문에 스크립트를 저장하면 다른 사용자가 목록·상세를 볼 때 실행되는 저장형 XSS가 발생한다.
- **설계단계 진단방법**: **아키텍처설계서·개발가이드**에 입력값/DB조회결과 출력 시 HTML인코딩 또는 XSS 필터링 규칙이 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 저장형 XSS 필터링 점검 계획이 있는지 확인한다.
- **결함 포인트**: 게시글 본문을 인코딩 없이 목록/상세에 출력하도록 설계한 경우.

### DSG-SC-01 — 세션통제
- **적용 이유**: 수정/삭제는 로그인 사용자만 수행해야 하므로 세션으로 사용자를 식별한다. 세션ID가 노출되거나 세션 간 데이터가 공유되면 타인 권한으로 수정/삭제가 가능해진다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 세션 간 데이터 비공유(컨트롤러/싱글톤 멤버변수 미사용), 로그아웃 시 세션 완전제거(invalidate), 재로그인 시 세션ID 변경, 세션ID를 안전한 난수로 생성하고 URL 비노출하는 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 세션 관리 점검 계획이 있는지 확인한다.
- **결함 포인트**: 세션ID를 URL에 노출하거나, 재로그인 시 세션ID를 갱신하지 않거나, 세션 검증 없이 글 ID만으로 수정/삭제를 처리하는 설계.

### DSG-EH-01 — 예외처리
- **적용 이유**: 권한 없는 요청·존재하지 않는 글 ID·DB 오류 등 예외가 발생하기 쉽다. 상세 에러가 노출되면 DB 구조·내부 로직이 드러난다.
- **설계단계 진단방법**: **요구사항정의서·개발가이드**에 명시적/런타임 예외를 예외처리 블록으로 안전하게 처리하고, 상세 에러정보 대신 지정 에러페이지로 리다이렉트하도록 설계되어 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 에러를 통한 정보노출 점검 계획이 있는지 확인한다.
- **결함 포인트**: 예외 발생 시 스택트레이스·SQL 오류 메시지를 사용자에게 그대로 노출하는 설계.

> 공통: 각 보안설계기준은 **요구사항정의서 → 아키텍처설계서 → 개발가이드 → 요구사항추적표 → 단위테스트케이스** 의 연결고리가 끊기지 않는지를 보는 것이 설계단계 진단의 핵심이다.
