## 💡 진단 해설

파일을 포함한 게시글 등록은 **첨부파일 업로드 + FAQ 내용 DB 저장(INSERT) + 목록 출력**이 결합된 기능이다. 가장 큰 위험은 위험 형식 파일(웹셸) 업로드이며, 게시글 본문/파일명의 저장형 XSS, INSERT 시 SQL 삽입도 함께 본다.

### DSG-IV-10 — 업로드·다운로드 파일 검증
- **적용 이유**: 화면이 첨부파일 업로드를 직접 받는다. 확장자/콘텐츠 검증 없이 저장하면 `.jsp/.php/.asp` 같은 실행 가능한 웹셸이 업로드되고, 웹 루트 하위에 원본 파일명으로 저장되면 URL로 직접 호출되어 서버가 장악된다.
- **설계단계 진단방법**: **요구사항정의서**에 업로드 파일의 타입·크기·개수·실행권한 제한 정책이 정의되어 있는지, **아키텍처설계서**에 ① 확장자 화이트리스트 검증 ② 외부 식별 불가능한 저장경로(URL 직접접근 불가 디렉터리) ③ 랜덤 저장 파일명과 업로드명↔저장명 DB 매핑 ④ 다운로드 시 요청파일명 경로조작 문자 필터링 및 허가된 사용자/파일 확인 설계가 있는지 확인한다. **개발가이드**에 프레임워크 업로드 크기 제한(예: Spring MultipartResolver `maxUploadSize`) 설정과 실행권한 제거 규칙이 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 위험형식 업로드 차단·경로조작 차단 점검 계획이 있는지 본다.
- **결함 포인트**: 확장자/콘텐츠 검증 누락, 웹 루트 하위에 원본 파일명 그대로 저장, 업로드 파일에 실행권한 유지, 다운로드 파일명 경로조작(`../`) 미필터링.

### DSG-IV-01 — DBMS 조회 및 결과 검증
- **적용 이유**: 저장 버튼 클릭 시 질문제목·내용·답변·파일메타정보를 DB에 INSERT하고 목록을 SELECT한다. 입력값이 쿼리 구조를 바꾸면 SQL 삽입이 발생한다.
- **설계단계 진단방법**: **요구사항정의서**에 정적쿼리 사용 대책, **아키텍처설계서**에 PreparedStatement/ORM 적용계획이 있고 **요구사항추적표**로 추적되는지, **개발가이드**에 동적쿼리 시 입력값 필터링 규칙이 있는지, **단위테스트케이스**에 입력값의 쿼리 구조 변경 여부 점검 계획이 있는지 확인한다.
- **결함 포인트**: 제목·내용을 문자열 결합으로 INSERT 쿼리에 넣는 동적 SQL 설계.

### DSG-IV-05 — 웹 서비스 요청 및 결과 검증
- **적용 이유**: FAQ 제목·내용·답변·파일명이 목록·상세 응답페이지에 출력된다. 본문/파일명에 스크립트를 저장하면 조회하는 사용자에게 저장형 XSS가 실행된다.
- **설계단계 진단방법**: **아키텍처설계서·개발가이드**에 입력값/DB조회결과 출력 시 HTML인코딩 또는 XSS 필터링 규칙이 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 저장형 XSS 필터링 점검 계획이 있는지 확인한다.
- **결함 포인트**: 게시글 본문·파일명을 인코딩 없이 출력하도록 설계한 경우.

### DSG-IV-06 — 웹 기반 중요기능 수행 요청 유효성 검증
- **적용 이유**: FAQ 저장(등록)은 DB에 데이터를 추가하는 중요기능이다. 검증이 없으면 위조된 등록 요청·자동화 스팸 등록이 가능하다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 세션별 CSRF 토큰 발급·검증, 필요 시 CAPTCHA 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 위조요청 차단 점검 계획이 있는지 확인한다.
- **결함 포인트**: 등록 요청에 정상요청 판별(토큰) 설계가 누락된 경우.

### DSG-SF-04 — 중요자원 접근통제
- **적용 이유**: FAQ 등록·답변은 권한 있는 사용자(관리자 등)만 수행해야 하고, 업로드 파일이 저장되는 디렉터리는 보호되어야 하는 중요자원이다.
- **설계단계 진단방법**: **요구사항정의서**에 FAQ 등록·업로드 기능에 대한 접근통제 정책(역할기반)과 저장 디렉터리 접근권한 최소화가 정의되어 있는지, **아키텍처설계서**에 적용계획이 있고 **요구사항추적표**로 추적되는지, **단위테스트케이스**에 권한 없는 등록 차단 점검 계획이 있는지 확인한다.
- **결함 포인트**: 인증·권한 검증 없이 누구나 FAQ를 등록·업로드할 수 있거나, 업로드 디렉터리에 과도한 권한을 부여한 설계.

### DSG-SC-01 — 세션통제
- **적용 이유**: 등록은 로그인 사용자만 수행해야 하므로 세션으로 사용자를 식별한다. 세션ID 노출·세션 간 데이터 공유가 있으면 타인 권한으로 등록이 가능하다.
- **설계단계 진단방법**: **요구사항정의서·아키텍처설계서**에 세션 간 데이터 비공유, 로그아웃 시 세션 완전제거, 재로그인 시 세션ID 변경, 안전한 난수 세션ID 생성·URL 비노출 설계가 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 세션 관리 점검 계획이 있는지 확인한다.
- **결함 포인트**: 세션ID를 URL에 노출하거나 재로그인 시 세션ID를 갱신하지 않는 설계.

### DSG-EH-01 — 예외처리
- **적용 이유**: 업로드 실패·용량초과·확장자 거부·DB 오류 등 예외가 빈번하다. 상세 에러가 노출되면 저장경로·DB 구조 등 내부 정보가 드러난다.
- **설계단계 진단방법**: **요구사항정의서·개발가이드**에 명시적/런타임 예외를 안전하게 처리하고 상세 에러정보 대신 지정 에러페이지로 처리하도록 설계되어 있는지, **요구사항추적표**로 추적되는지, **단위테스트케이스**에 에러를 통한 정보노출 점검 계획이 있는지 확인한다.
- **결함 포인트**: 업로드·저장 예외 발생 시 파일 절대경로·스택트레이스·SQL 오류를 그대로 노출하는 설계.

> 공통: 각 보안설계기준은 **요구사항정의서 → 아키텍처설계서 → 개발가이드 → 요구사항추적표 → 단위테스트케이스** 의 연결고리가 끊기지 않는지를 보는 것이 설계단계 진단의 핵심이다.
