# 실습 09 — 버퍼 오버플로우 방지 개발가이드 진단

> 출처: KISEC 2026 기본과정 교재 p325–326 (Ⅳ-02 보안설계 기준 및 설계 기준 실습)
> 형식: 참고자료(p325 「C 오버플로우를 방지하기 위해 작성한 개발가이드」)를 보고 **p326 진단 양식**을 채우는 실습
> 유형: **개발가이드 진단** — 화면정의가 아니라, 제출된 개발가이드 문서에 담긴 설정값·기법 설명이 보안기준에 부합하는지 진단한다.

### 식별된 결함 상세

| # | 가이드 기재값 | 결함 | 올바른 값(개선) |
|---|-------------|------|----------------|
| ❶ | 윈도 ASLR을 `/DYNAMICBASE` **"NO"** 로 설정 | ASLR을 **끄는** 설정. 주소 무작위화가 무력화됨 | `/DYNAMICBASE` **"YES"** (IMAGE_BASE 가변) |
| ❷ | 리눅스 `randomize_va_space` = **0** | 값 0은 ASLR **비활성**. 1(부분)·2(전체)가 활성 | `2`(권장) 또는 최소 `1` |
| ❸ | 리눅스 DEP "비활성화 옵션을 적용한 경우 그 옵션을 제거" | 서술 자체는 활성화를 지향하나, 디폴트 활성 전제만 신뢰해 **검증 절차가 없음** | 빌드 산출물의 NX bit 활성을 명시적으로 점검하는 절차 추가 |
| ❹ | 「안전한 함수의 예: `gets`, `strcpy`, `strcat`, `sprintf`」 | 나열된 것은 모두 경계검사 없는 **취약(위험) 함수**. 안전/위험 분류가 정반대 | 「사용 금지 함수」로 분류, 대체: `fgets`, `strncpy`/`strlcpy`, `strncat`/`strlcat`, `snprintf` |

> DEP(`/NXCOMPAT`, `SetProcessDEPPolicy`)와 카나리(`GS`, `-fstack-protector`) 옵션 자체는 올바르게 기재됨.

## 💡 진단 해설

**① 가이드가 제시한 내용** — 버퍼 오버플로우 방지를 위해 ASLR·DEP·스택 카나리 3종 보호기법을 OS별로 설명하고, 마지막에 "안전한 함수의 예"를 든다. 진단 대상은 이 가이드 문서다(설계산출물 진단).

**② 보안기준 충족 여부 — 미적용(N)** — DSG-IV-08은 ASLR·DEP·StackGuard 등 메모리 보호정책이 **적용**되도록 시큐어코딩 규칙을 정의할 것을 요구한다. 그러나 본 가이드는 보호기능의 **on/off 값을 반대로 기재**했다.
- ASLR: 윈도 `/DYNAMICBASE`는 "YES"가 활성인데 가이드는 **"NO"**(끔)로 안내. 리눅스 `randomize_va_space`는 1·2가 활성인데 **0**(끔)으로 안내. → 주소 무작위화가 전혀 동작하지 않아 쉘코드/시스템함수 주소 예측이 다시 가능해진다.
- 위험 함수: `gets`·`strcpy`·`strcat`·`sprintf`는 경계검사가 없어 버퍼 오버플로우를 유발하는 대표적 **사용 금지 함수**인데, 가이드는 이를 "안전한 함수의 예"로 안내한다. DSG-IV-08의 보안대책 ②(취약 API 사용 금지)에 정면으로 위배된다. 개발자가 가이드를 그대로 따르면 취약점을 양산하게 된다.

**③ 설계단계 진단방법** — 개발가이드(시큐어코딩 규칙)에 ⓐ 메모리 보호정책 활성화 옵션이 **정확한 값**으로 기재되어 있는지, ⓑ 위험 함수 목록과 안전한 대체 함수가 「금지/권장」으로 올바르게 분류되어 있는지를 검토한다. 요구사항정의서에 대책이 수립되고, 아키텍처설계서에 적용계획이 있으며, 요구사항추적표로 추적 가능한지 확인한다. 옵션 값의 정오(正誤)는 OS 벤더 문서·KISA 시큐어코딩 가이드 기준으로 대조한다.
