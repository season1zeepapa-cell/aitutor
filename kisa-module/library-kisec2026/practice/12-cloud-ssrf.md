# 실습 12 — 클라우드 애플리케이션의 SSRF 방어 설계 진단

> 출처: KISEC 2026 기본과정 교재 p331–332 (Ⅳ-02 보안설계 기준 및 설계 기준 실습)
> 형식: 참고자료(p331 화면정의 SP-ARCH-01)를 보고 **p332 진단 양식**을 채우는 실습
> 유형: **아키텍처/데이터흐름 진단** — 클라우드 데이터 흐름 설계가 SSRF(서버사이드 요청 위조)를 방어하는지 진단한다.

## 📄 참고자료 요약 (p331 아키텍처 정의)

| 항목 | 내용 |
|------|------|
| ID | SP-ARCH-01 |
| 화면명 | 클라우드 데이터 흐름 |
| 업무시스템 | 전자정부 프레임워크 공통컴포넌트 |
| 업무기능 | 요청 및 응답 데이터 흐름 |
| 단위시스템 | 클라우드 데이터 처리 |

**데이터 흐름 설계 (처리개요)**
1) 인터넷 관문을 통해 입력되는 파라미터에 대하여 **검증을 수행**한다.
2) **Public subnet** 에서 **Private subnet** 에 위치한 서버로 파라미터를 전달한다.
3) Private subnet의 서버가 **Private storage** 에 저장된 콘텐츠에 접근한다.

## ✅ 채운 양식 — 진단 결과

| 항목 | 진단 내용 |
|------|------|
| **진단 대상** | 클라우드 데이터 흐름의 SSRF 방어 설계(SP-ARCH-01) |
| **분류** | ☑ 입력데이터 검증 및 표현 (□ 보안기능 □ 에러처리 □ 세션통제) |
| **보안설계기준** | **HTTP 프로토콜 유효성 검증** (DSG-IV-07), **시스템 자원 접근 입력값 검증** (DSG-IV-04) — 서버사이드 요청 위조(SSRF) 방어 |
| **기준 설명** | 외부입력값이 서버 측 요청 대상(URL·IP·리소스)을 결정하는 경우, 허용된 목록의 선택자로만 사용하고 허가되지 않은 내부 자원에 접근하지 못하도록 검증·격리해야 한다. |
| **진단 결과** | ☑ **Y(적용, 단 조건부)** — 입력 검증 + subnet 분리(Public/Private)로 SSRF 방어의 핵심 통제가 설계에 반영됨. 다만 검증 방식의 구체성·예외 우회 대응을 보완해야 한다 |
| **현황 및 문제점** | (아래 ❶~❸) 파라미터 검증 수행·망 분리(Public→Private)·저장소 격리는 적절. 인코딩/파서 우회 차단과 화이트리스트 명시가 추가 점검 필요 |
| **관련 산출물** | 아키텍처설계서(망 구성도), 데이터흐름도, 인터페이스 설계서, 요구사항추적표 |
| **개선 방안** | 요청 대상 URL/IP를 화이트리스트 선택자로 제한, 인코딩·IDNA·파서 우회 정규화 후 검증, 내부 메타데이터 엔드포인트 접근 차단 |

### 진단 포인트 상세

| # | 설계 내용 | 평가 | 비고 |
|---|----------|------|------|
| ❶ | 인터넷 관문 입력 파라미터 **검증 수행** | ✅ 적절 (DSG-IV-07 ②) | 단, 검증을 "허용 URL 목록 선택자"로 한정하는지 확인 필요 |
| ❷ | **Public subnet → Private subnet** 망 분리 후 파라미터 전달 | ✅ 적절 | 외부가 내부 서버에 직접 도달하지 못하게 하는 SSRF 격리 핵심 |
| ❸ | Private subnet 서버만 **Private storage** 접근 | ✅ 적절 | 저장소를 외부 비공개로 격리 |
| ⚠ | 인코딩/IDNA2003/Broken Parser **우회** 대응 | 추가 점검 | 교재 §12 SSRF 예시(인코딩·IDNA 변환·파서 불일치)로 화이트리스트가 우회될 수 있음 |
| ⚠ | 클라우드 **메타데이터 엔드포인트**(예: 169.254.169.254) 접근 차단 | 추가 점검 | SSRF의 대표 표적, 명시적 차단 설계 권고 |

## 💡 진단 해설

**① 설계서가 제시한 내용** — 인터넷에서 들어오는 파라미터를 검증한 뒤, Public subnet에서 Private subnet 서버로만 전달하고, Private 서버만 Private storage에 접근하는 3계층 데이터 흐름이다. 진단 대상은 이 아키텍처가 SSRF를 방어하는지다.

**② 보안기준 충족 여부 — 적용(Y, 조건부)** — 앞선 09~11과 달리 본 실습은 **적합 사례**에 가깝다. SSRF 방어의 두 축인 ⓐ 입력값 검증(DSG-IV-07 ②: 허용된 URL 목록 선택자로만 사용)과 ⓑ 망/자원 격리(외부→내부 직접접근 차단, DSG-IV-04 ①: 허가되지 않은 자원 접근 방지)가 설계에 모두 반영되어 있다.
- ❶ 관문에서 파라미터를 검증하므로 임의 URL/IP 주입 시도를 1차로 거른다.
- ❷ Public→Private subnet 분리로 외부 요청이 내부 서버에 직접 도달하지 못한다. SSRF는 "서버가 공격자 지정 내부 주소로 요청을 보내게" 하는 공격이므로, 내부 망을 외부와 분리하는 것이 구조적 방어가 된다.
- ❸ 저장소를 Private에 격리해 외부 노출면을 최소화한다.

**보완 필요(⚠)** — 교재 §12(서버사이드 요청 위조)는 문자열 인코딩, IDNA2003 변환, Broken Parser를 이용한 SSRF 우회 사례를 든다. 따라서 "검증 수행"이 단순 문자열 매칭이면 인코딩·도메인 변환으로 화이트리스트를 우회당할 수 있다. ⓐ 입력을 정규화(canonicalize)한 뒤 검증하고, ⓑ 허용 대상은 화이트리스트 선택자로 제한하며, ⓒ 클라우드 메타데이터 엔드포인트(169.254.169.254 등 링크로컬·사설 대역) 접근을 명시적으로 차단하도록 설계를 보강해야 한다.

**③ 설계단계 진단방법** — 아키텍처설계서의 망 구성도·데이터흐름도에서 ⓐ 외부 입력이 내부 자원 식별에 직접 쓰이지 않는지, ⓑ Public/Private subnet 분리와 저장소 격리가 도식상 명확한지, ⓒ 입력 검증이 정규화 후 화이트리스트 방식인지, ⓓ 메타데이터/사설대역 차단 정책이 있는지를 검토한다. 인터페이스 설계서·요구사항추적표로 SSRF 방어 대책의 적용 여부를 추적한다.
