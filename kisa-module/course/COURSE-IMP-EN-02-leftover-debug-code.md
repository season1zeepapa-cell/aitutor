# 제거되지 않고 남은 디버그 코드

- **코드**: COURSE-IMP-EN-02 (chapter ref: IMP-EN-02)
- **단계**: Ⅴ. 구현 단계 보안약점 진단
- **분류**: 캡슐화(encapsulation)
- **출처**: 2025년 SW보안약점 진단원 기본(양성)과정, 483-484쪽

## 요약

디버깅을 목적으로 삽입된 코드가 제거되지 않고 남아 있는 경우 발생하는 캡슐화 보안약점이다. 디버그 코드는 설정 등 민감한 정보를 포함하거나 시스템 제어를 허용하는 부분을 담고 있을 수 있어, 배포 시 공격자가 식별 과정을 우회하거나 의도하지 않은 정보·제어 정보가 노출될 수 있다.

## 개요 — 약점 정의

- 디버깅을 목적으로 삽입된 코드가 제거되지 않고 남아 있는 경우 발생한다.
- 디버그 코드는 설정 등의 민감한 정보를 포함하고 있거나 시스템을 제어하게 허용하는 부분을 담고 있을 수 있다.
- 디버그 코드가 남겨진 채로 배포될 경우, 공격자가 식별 과정을 우회하거나 의도하지 않은 정보와 제어 정보가 노출될 수 있다.

## 보안대책

- SW 배포 전, 반드시 디버그 코드를 확인하고 삭제한다.
- 애플리케이션 제작 시 디버그 용도로 개발한 `main()` 함수는 디버깅이 끝나면 삭제한다.

## 진단 흐름도

1. `main()` 등 디버그 코드 확인.
2. 디버그 코드가 **없음** → 안전.
3. 디버그 코드가 **있음** → 위험.

## 코드 예시 — main() 디버그 코드 제거

**안전하지 않은 코드**
```java
class Base64 {
   // J2EE의 경우 main() 메소드 사용이 필요 없으며, 개발자들이 콘솔 응용프로그램으로
   // 화면에 디버깅코드를 사용하는 경우가 일반적임
   public static void main(String[] args) {
      if (debug) {
          byte[] a = { (byte) 0xfc, (byte) 0x0f, (byte) 0xc0 };
          byte[] b = { (byte) 0x03, (byte) 0xf0, (byte) 0x3f };
      }
   }
   public void otherMethod() { … }
}
```

**안전한 코드**
```java
class Base64 {
   public void otherMethod() { … }
}
```

## 시험 포인트

- 원인: 디버깅 목적으로 삽입된 코드가 제거되지 않고 남아 있음.
- 위험: 민감 정보 노출, 식별 과정 우회, 의도하지 않은 제어 정보 노출.
- 보안대책: SW 배포 전 디버그 코드 확인·삭제, 디버그용 `main()` 함수 삭제.
- J2EE에서는 `main()` 메소드 사용이 필요 없음 — 콘솔 디버깅용 `main()`이 대표적 잔존 코드.
- 진단 흐름: `main()` 등 디버그 코드가 있으면 위험.
