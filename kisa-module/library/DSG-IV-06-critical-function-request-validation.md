# DSG-IV-06 · 웹 기반 중요 기능 수행 요청 유효성 검증

> **단계** 설계 · **분류** 입력데이터 검증 및 표현
> **출처** 소프트웨어 보안약점 진단가이드(2021) — 제3장 §1.6 (p.71–75)
> **연관 구현약점** 크로스사이트 요청 위조 (CSRF)

## 설계항목 / 설명

비밀번호 변경, 결제 등 사용자 권한 확인이 필요한 중요기능을 수행할 때 웹 서비스 요청에 대한 유효성 검증방법 설계 및 유효하지 않은 값에 대한 처리방법을 설계해야 한다.

## 보안대책

- ① 시스템으로 전송되는 모든 요청에 대해 **정상적인 사용자의 유효한 요청인지** 여부를 판별할 수 있도록 해야 한다.

## 가. 취약점 개요

공격자는 세션탈취, XSS 등으로 자신이 의도한 행위(수정, 삭제, 등록 등)를 사이트가 신뢰하는 인증된 사용자의 권한으로 실행되게 할 수 있다(CSRF). 웹은 URL 기반으로 요청을 처리하는 구조이므로, 요청이 특정 사용자의 정상 요청인지 구분하는 정책이 없으면 스크립트·자동화 도구가 보내는 요청이 검증 없이 처리될 수 있다.

## 나. 설계 시 고려사항

1. **CSRF 토큰 사용** — 세션별 CSRF 토큰을 생성·저장하고, 작업페이지 요청 시 hidden값으로 전달한 뒤 데이터처리 요청 시 전달 토큰과 세션 토큰을 비교 검증. MVC프레임워크(Spring·Struts) Interceptor로 자동 검사하도록 설계.
   - 대응 프레임워크/라이브러리: Java(Spring Security 3.2+·Apache Struts·OWASP CSRFGuard), Python(Django), PHP(CSRF Protector)
2. **사용자와 상호 처리 기능 적용** — CSRF 토큰도 XSS 취약점 사이트에서는 무력화될 수 있으므로 CAPTCHA 등 상호 처리 기법 적용
3. **재인증 요구** — 중요기능은 재인증으로 실제 요청 여부 확인

## 다. 진단 세부사항 (요구사항별 체크리스트)

> 📋 각 진단방법은 **관련산출물 검토예시**와 짝을 이룬다 — 이것이 복합서술형(진단보고서) 채점 기준이 된다.

### 요구사항 ① 모든 요청의 유효성 판별
- **Q1. 중요기능 요청에 대한 데이터 처리 요청에 대해 요청 유효성을 판단하여 처리할 수 있도록 설계되어 있는가?**
  - `1-1` 요구사항정의서 대책 + 아키텍처설계서 적용계획 + 요구사항추적표 추적 → **요구사항정의서·요구사항추적표·아키텍처설계서**
  - `1-2` 정상 절차 요청 검증 기능(CSRF 토큰·CAPTCHA) 안전 설계 → **프로그램명세서·클래스설계서·아키텍처설계서**
  - `1-3` 요청유효성 점검 기능 안전 적용(모든 요청 / 각 기능 적용) → **아키텍처설계서 보안요구항목**, 개별 적용 시 **클래스설계서·개발가이드**
  - `1-4` 주요기능 재인증/재인가 방법·모듈 설계 → **클래스설계서**
- **Q2. 요청 유효성 검증 기능 점검 테스트 계획이 수립되어 있는가?**
  - `2-1` 자동화 스크립트·프로그램의 자동 요청 식별·차단 점검 테스트 계획 → **단위테스트케이스**
